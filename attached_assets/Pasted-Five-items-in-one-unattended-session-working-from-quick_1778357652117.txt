"The scheduler tick checks nightlyJob.status === 'running' before triggering, but doesn't lock per-day. If the server restarts during the scheduled hour, the chain could fire twice in one day. Add stats.last_run_day check."

File: artifacts/api-server/src/lib/scheduler.ts (probably). The scheduler tick logic and the jobs row for "nightly_sync".

  3. Add a guard: before triggering, check if the current local-club-date matches a "last_run_day" field in jobs.stats. If yes, skip (already ran today). If no, proceed and write last_run_day = today after a successful chain completion.

Implementation requirements:

  - Atomic update — if the scheduler checks last_run_day, finds today doesn't match, but a parallel tick is already mid-run, we still need the existing nightlyJob.status === "running" check to prevent concurrent fires. Both guards are needed; they protect against different scenarios (status = concurrent fires within a tick window; last_run_day = re-fire after restart).

ITEM E — Tier 5 S8: decouple link_strategy from heuristic top program
────────────────────────────────────────────────────────────
This is the largest item and the one most likely to surface scope. From the runbook:

"The agent route picks a top program heuristically before Claude runs, computes warm_score against it, and uses that score for link_strategy. Claude often recommends a different program, and the link_strategy was scored against the wrong one."

File: artifacts/api-server/src/routes/agent.ts.

The fix has two viable shapes per the runbook:
  Option 1: Compute link_strategy AFTER Claude makes the recommendation. Re-score against the program Claude actually picked.
  Option 2: Score against all candidates and surface them all; Claude picks; link_strategy comes from the scored entry that matches.

Decision: I want Option 1. It's smaller, simpler, and matches the existing flow (Claude picks, then we use what Claude picked). Option 2 is closer to a multi-program rework.

Plan:
  1. Read agent.ts. Find:
     a. Where the heuristic top program is selected (pre-Claude)
     b. Where computeWarmScore is called against it
     c. Where scoreToLinkStrategy is called (this is what we're moving)
     d. Where Claude's recommended_programs[0] is resolved against the program list (this exists — used for signup_url lookup)
  2. The new flow:
     a. Pre-Claude: keep the heuristic top program selection (Claude needs context). Pass programs to Claude as before.
     b. Pre-Claude: compute warm_score against the heuristic top program — KEEP this for context passed into the prompt (the "warm score" the player sees in the prompt).
     c. POST-Claude: after agentResponse parses, look up the program Claude actually recommended (firstRecommendedName lookup, already exists on line 428-ish).
     d. POST-Claude: compute link_strategy from a re-scored warm_score against THAT program. NOT from the pre-Claude warm_score against the heuristic top.
     e. Stitch the post-Claude link_strategy into the response body, replacing whatever the current code returns.
  3. Edge case: Claude might recommend a program not in the available list (paraphrased name, hallucinated name). Today's lookup at line 428 handles this with .find(), which returns undefined. If undefined, fall back to the pre-Claude link_strategy. Don't fail the request.
  4. Edge case: Claude might recommend NO program (recommended_programs is empty — e.g. new player welcome, no pitch). In that case, link_strategy doesn't matter (there's no link to send). Set link_strategy to "soft" or null and document the choice in a comment.

Verify:
  - tsc clean
  - Walk through three scenarios in your head:
    1. Claude picks the heuristic top program: link_strategy is identical to before (no behavior change for the common case)
    2. Claude picks a different program: link_strategy reflects the actual recommendation
    3. Claude picks no program / unresolvable name: graceful fallback, no error
  - If you have a known test player from earlier sessions, fire one agent request and inspect the response. Confirm link_strategy is sane and the message body matches the recommendation.
  - Send back the diff and the three scenarios.

If the refactor touches more than ~30 lines or requires moving warm_score computation out of the Promise.all data fetch: STOP and DEFER. That's a bigger re-plumbing that needs a fresh design pass.
