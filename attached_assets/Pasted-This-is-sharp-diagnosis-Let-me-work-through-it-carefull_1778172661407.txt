If all four test players were imported in the same batch ~13 days ago, all four hit this branch and return 0 regardless of attendance history. That's exactly what the logs confirmed.
But here's the deeper bug — created_at in the players table is the database insert timestamp, not the date the player joined the club. When importAllPlayers.js runs and creates new player rows, it sets created_at to "now" — meaning every player imported during a fresh setup looks like a brand-new player to the warm-score logic. The "<14 days" check was designed to protect real new members from premature warm scoring, but it's being triggered by data-import recency.
This is a real production-blocker. The day you import 2,006 players from PodPlay's history, every single one of them is a "new player" for 14 days as far as warmScore.ts is concerned. Nobody gets a meaningful warm score during launch week.
The fix is to use a different source of truth for "is this a real new member":

Best: Use the player's first attendance date. If their first attendance is < 14 days ago, they're new. This is robust to imports — a 5-year veteran whose data was imported yesterday has a first_attended_at from 5 years ago, so the branch correctly skips.
Second best: Add a joined_at column to players, distinct from created_at. Source it from PodPlay's user-creation timestamp during import. This requires a migration and a re-import to populate.
Cheapest hack (don't do this): Tighten the threshold to "< 7 days." Doesn't actually solve the problem, just narrows the window.

Option 1 is the right call. It's also a one-query change in warmScore.ts — no migration, no re-import, no extra data dependencies. We're already fetching attendances anyway.
