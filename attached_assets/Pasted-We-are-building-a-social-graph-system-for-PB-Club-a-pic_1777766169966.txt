We are building a social graph system for PB Club, a pickleball 
facility. The goal is to programmatically build community by 
tracking which players have shared court time together and using 
those relationships to:

1. Help the retention agent personalize outreach — instead of 
   generic "come back" messages, the agent can say "Sarah K. and 
   Mike T. are signed up for Thursday's session"
2. Give staff a 7-day ahead view of upcoming sessions so they can 
   make intentional introductions — "Alex is coming tonight for 
   only his 2nd visit and Jamie, who he's played with twice before, 
   is also in tonight's session"
3. Eventually power opt-in buddy notifications (not in this build)

The system has three components:
- Buddy pairs — players who have shared 3+ sessions together
- Agent context — buddy data fed into the retention agent prompt
- Staff intro panel — a dashboard view for coaches to plan 
  connection moments

CREATE TABLE IF NOT EXISTS buddy_pairs (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  player_a uuid REFERENCES players(id) ON DELETE CASCADE,
  player_b uuid REFERENCES players(id) ON DELETE CASCADE,
  shared_sessions integer DEFAULT 0,
  last_shared_at timestamptz,
  opt_in_notifications boolean DEFAULT false,
  updated_at timestamptz DEFAULT now(),
  UNIQUE(player_a, player_b),
  CHECK (player_a < player_b)
);

ROUTE A: POST /api/social-graph/compute-buddy-pairs
This is the historical computation — who has played together 
3+ times based on past attendance records in Supabase.

1. Pull all attendances from last 90 days from Supabase:
   SELECT player_id, event_id, attended_at FROM attendances
   WHERE attended_at >= now() - interval '90 days'
   AND player_id IS NOT NULL
2. Group by event_id → build map of event_id → player_id[]
3. For every pair in the same event, enforce player_a < player_b 
   (sort UUIDs alphabetically), increment shared_sessions counter 
   in a JS Map keyed "playerA:playerB", track most recent 
   attended_at as last_shared_at
4. For pairs with shared_sessions >= 3, upsert into buddy_pairs 
   in batches of 100
5. Return { pairs_updated: N, pairs_below_threshold: M }

ROUTE B: GET /api/social-graph/player/:id/buddies
1. Query buddy_pairs WHERE player_a = id OR player_b = id
   ORDER BY shared_sessions DESC LIMIT 10
2. Resolve the other player's name from players table
3. Return { buddies: [{ player_id, name, shared_sessions, 
   last_shared_at, opt_in_notifications }] }

ROUTE C: GET /api/social-graph/upcoming-with-buddies/:id
This is the forward-looking query — for a given player, find 
upcoming sessions where their buddies are already registered.
Use the PodPlay upcoming events + attendees endpoints confirmed 
in Step 1.

1. Get this player's buddies from buddy_pairs (all, not just 
   opt-in — we're showing context to staff and agent, not 
   texting anyone yet)
2. Get upcoming events for the next 7 days from PodPlay
3. For each upcoming event, call the attendees endpoint
4. Cross-reference attendee list with buddy player external_ids
   (need to join players table to get external_id for each buddy)
5. Return events where at least one buddy is registered:
   {
     upcoming: [{
       event_id, program_name, level, start_time,
       buddies_signed_up: [{ player_id, name, shared_sessions }]
     }]
   }
Rate limit: 250ms delay between PodPlay attendee calls

ROUTE D: GET /api/social-graph/staff-intro-cards
7-day rolling window of upcoming sessions with new player flags 
and buddy connection data. Used by the staff dashboard panel.

1. Get upcoming events for next 7 days from PodPlay
2. For each event get the registered attendee list
3. For each attendee, look up their player record in Supabase 
   by external_id to get visit_count (total attendance count)
4. Flag players with visit_count <= 3 as new
5. For new players, query buddy_pairs to find any buddy 
   connections who are also registered for this same event
6. Group by date, return:
   {
     cards: [{
       event_id, program_name, level, start_time,
       new_players: [{
         player_id, name, visit_count,
         buddy_connections: [{ player_id, name, shared_sessions }]
       }]
     }]
   }
   Only include events that have at least one new player.
   Sort by start_time ascending.
   Rate limit: 250ms between attendee calls.

ROUTE E: POST /api/social-graph/test/compute-now
Calls compute-buddy-pairs and returns result synchronously.
No body required. Dev/test only.

// Step 4: Buddy pair graph update
try {
  await appendJobLog(JOB_NIGHTLY, "Step 4: updating buddy pair graph");
  const res = await fetch(
    "http://localhost:3000/api/social-graph/compute-buddy-pairs", 
    {
      method: "POST",
      signal: AbortSignal.timeout(5 * 60 * 1000),
    }
  );
  const result = await res.json();
  await appendJobLog(JOB_NIGHTLY,
    `Step 4 complete — pairs updated: ${result.pairs_updated}`);
} catch (err: any) {
  await appendJobLog(JOB_NIGHTLY,
    `Buddy pair update error (non-fatal): ${err.message}`);
}
