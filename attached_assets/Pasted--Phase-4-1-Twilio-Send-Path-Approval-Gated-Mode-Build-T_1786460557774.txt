# Phase 4.1 — Twilio Send Path (Approval-Gated)

**Mode:** Build. This phase creates the first code in the project that can actually send a message.
**Scope:** 5 items, sequential. Item 1 gates everything — the existing send path must be verified end-to-end before anything is pointed at a list.

---

## Context

The experiment module (Phase 4) prepares candidates, randomizes treatment/control, drafts messages, and measures outcomes. The operator currently sends by hand. This phase replaces the copy-paste step with a single approved dispatch.

**The Twilio integration already exists.** Pulse has a working send path gated behind `SMS_LIVE` (defaults false), with `SMS_TEST_OVERRIDE_TO` for redirecting to a test number, and the A2P 10DLC campaign is approved on **`+12015281834`**.

**Verify the configured sending number before Item 1c.** Project notes previously recorded `+19129134807`; the approved number is `+12015281834`. Report which number the code and environment are actually configured with. If it is the old one, correct it — sending from an unapproved number will fail or, worse, send from a sender with no campaign association. This phase connects the experiment module to that infrastructure — it is not building an integration from scratch. **Read the existing send path first and reuse it.** Do not write a second Twilio client.

**What changes materially is the risk profile.** Pulse sends one message to one player, operator-initiated, one at a time. Bulk send is a different failure mode: a bug in list construction dispatches 20 wrong messages instantly and they cannot be recalled. The safeguards in Item 3 exist because of that difference.

**Approval model, as decided:** the operator reviews the full list, clicks send once, and the system dispatches. Human gate on *who*; automation only removes the tedium of sending twenty messages by hand. No experiment ever dispatches without explicit approval.

---

## Hard constraints

**1. No PodPlay writes.** No `POST`/`PATCH`/`PUT`/`DELETE`. Do not touch `lowTurnoutAutoCancel*`. Do not call `POST /events/{eventId}/cancellation` in any mode, including `PREVIEW`.

**2. `SMS_LIVE` stays `false` for the entire phase except during the Item 1 self-test**, and returns to `false` immediately after. Every other item is built and verified against the disabled path.

**3. No scheduled or automatic sending.** No timer, no cron, no nightly-chain wiring. Dispatch happens only in response to an explicit operator approval action.

**4. Supabase writes** limited to the experiment tables, `contact_ledger`, and `messages` (send records). Do not modify `players`, `attendances`, `conversations`, `event_fill`, or `sms_consent_records`.

**5. Never echo full phone numbers** in report output. Masked only. The UI may display them to the operator.

**6. Never echo secrets** — no Twilio SID, auth token, or API keys in output or logs.

---

Item 1 must complete and be reported before Item 2. If the self-test fails, stop and report — a send path that can't deliver to a known-good number must not be pointed at a member list.

## Item 2 — Experiment dispatch endpoint

**2a. One endpoint**, e.g. `POST /api/experiments/:id/send`, that dispatches the approved treatment arm.

Preconditions, checked server-side, every one of which aborts the whole batch:
- experiment `status = 'ready'` — never `draft`, never already `sent`
- an explicit approval token or flag in the request body; the endpoint must not fire on a bare POST
- every recipient is `arm = 'treatment'`, `vetoed = false`, `sent_at IS NULL`
- every recipient is SMS-reachable and consented
- batch size within the hard cap (Item 3)

**2b. Per-message, in order:** re-check the recipient against the preconditions, send, write the `messages` row, write the `contact_ledger` row (`source='experiment'`, `purpose='promotion'`, with `experiment_id`), set `sent_at` on the participant.

**2c. Partial failure must not corrupt state.** If message 12 of 20 fails, the first 11 stay sent and recorded, 12 is marked failed with its error, and 13–20 continue. Report per-recipient outcome. **Never re-send on retry** — `sent_at IS NULL` is the guard, and it must be checked immediately before each send, not once at batch start.

**2d. Idempotent.** Calling the endpoint twice must not double-send. Verify by calling it twice against the disabled path and confirming the second call dispatches zero.

**2e. Rate limiting.** Space sends to stay within Twilio's throughput. Report the pacing used.

## Item 3 — Safeguards

These exist because bulk send fails differently than single send.

**3a. Hard batch cap, independent of the rules.** If a dispatch would exceed **50 recipients**, abort the entire batch and report. This is a code-level guard against a bad query, not a tunable setting, and it should not read from `programming_rules`.

**3b. Test-number override honored by the experiment path**, not just Pulse's. When `SMS_TEST_OVERRIDE_TO` is set, every message in the batch goes to that number instead, with the intended recipient recorded in the `messages` row. **Your first real experiment run should land 20 messages on your own phone.**

**3c. Control-arm exclusion checked at the send call.** Not only at list build. A control member receiving a message through any path invalidates the experiment, and an automated sender is exactly where that leak happens. Verify explicitly: attempt to include a control participant and confirm the batch aborts.

**3d. Global kill switch, readable from the database.** Not just an env var — during an incident the operator needs one UPDATE, not a redeploy. Checked immediately before each individual send, not once at batch start.

**3e. Consent re-check at send time.** A player who opted out between list build and dispatch must not receive a message. Check `sms_opt_in` and opt-out status per recipient at send.

**3f. Dry-run mode.** `dryRun: true` runs every precondition and returns exactly what would be sent, to whom, without dispatching. This is what the operator sees before approving.

## Item 4 — Approval UI

**4a. Approval is explicit and specific.** Not a generic "Send" button. The operator sees a confirmation naming the count, the arm, the session, and whether the test override is active — e.g. *"Send 21 messages to treatment arm for Tuesday 6pm Open Play. Test override ACTIVE — all messages route to +1201•••2546."* They confirm that.

**4b. Override state must be unmissable.** When `SMS_TEST_OVERRIDE_TO` is set, the UI shows it prominently. When it is not — meaning messages go to real members — that must be even more prominent. The single worst outcome in this phase is the operator believing they are in test mode when they are not.

**4c. Post-send state.** Per-recipient status: sent, failed with error, or pending. Delivery status updated as Twilio callbacks arrive, if the webhook is wired.

**4d. No re-send button.** If a message fails, it is investigated, not retried from the UI. Retry logic is a later decision.

**4e. Control arm stays visible** and clearly labeled *"Do not contact — held out 30 days."*
