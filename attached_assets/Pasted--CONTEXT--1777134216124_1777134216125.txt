This is the Pulse retention dashboard for PB Club, a 
pickleball club management tool. The stack is:
- Frontend: React + TypeScript + Tailwind (Vite)
- Backend: Node.js / Express API
- Database: Supabase (PostgreSQL)
- SMS: Twilio

The Players page already has a working filter bar with these 
filters: engagement state (Active / Lapsing / Dormant / Never 
Visited), progression status, membership, skill level, and a 
name search. Filters produce a live client-side filtered array 
of players already in React state.

The players table in Supabase has these relevant columns:
  id, first_name, last_name, phone, skill_level,
  engagement_state, progression_status, membership_status,
  last_visit_date, sms_opt_in, external_id

GOAL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Build a Bulk Message Writer feature. This lets a club operator 
filter a group of players on the Players page, click "Send bulk 
message", and compose + send a personalized SMS to every player 
in the filtered list. Messages can use saved templates (built-in 
or user-created) with dynamic variables that auto-fill per player 
at send time (e.g. first name, skill level). Use cases include 
win-back campaigns for lapsed players, tournament promotions 
targeted by skill level, and clinic invites for players ready 
to advance.

- Renders the message body with variables replaced by

    {{skill_level}} → first recipient's skill_level

    {{event_date}} → "May 10"

- Toggle: "Only send to SMS opt-in players" (default ON).
- When ON: eligible count = recipients where sms_opt_in = true.
- When OFF: eligible count = all recipients.
- Show: "44 / 47 eligible" dynamically.

- Right side: [Cancel] [Send to N players →]

  "Send to N players" button triggers Section 4's send logic.
  Button is disabled if no template selected / message empty

SECTION 4 — API: POST /api/messages/bulk endpoint
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
In the Express server, add POST /api/messages/bulk.

Request body:
  {
    player_ids: string[],      // array of player UUIDs
    message_body: string,      // raw body with {{variables}}
    template_id?: string       // optional, for logging
  }

Server logic:
1. Fetch each player record from Supabase by id 
   (only those with sms_opt_in = true).
2. For each player, interpolate the message_body:
   - Replace {{first_name}} with player.first_name
   - Replace {{skill_level}} with player.skill_level 
     or "your level" if null
   - Replace {{last_visit}} with formatted last_visit_date 
     or "a while" if null
   - Replace {{club_name}} with "PB Club"
   - Leave {{event_date}} and {{booking_link}} as-is 
     (operator fills these in the template or message body 
     before sending)
3. Send each SMS via Twilio (same pattern as existing 
   single-send logic already in the codebase).
4. For each send, insert a row into the messages table 
   (same schema as existing messages) with:
     direction: "outbound"
     sent_by: "operator"
     body: the interpolated message text
     player_id: the player's id
     status: "sent" or "failed"
5. Return:
   {
     sent: number,
     failed: number,
     errors: string[]   // any player IDs that failed
   }

Rate-limit sends: add a 100ms delay between each Twilio 
call to avoid hitting API limits on large batches.

1. Call POST /api/messages/bulk with the eligible player

2. On success: close the modal and show a toast:
   "✓ Sent to 44 players" in green, auto-dismiss 5s.
   If any failed: "✓ Sent to 42 players · 2 failed" 
   in amber with a "See details" link that logs to console 
   for now.
3. On network error: show a toast "Send failed — try again" 
   in red. Do not close the modal so the user can retry.
4. Use the existing toast system already in the app — 
   do not add a new library.
