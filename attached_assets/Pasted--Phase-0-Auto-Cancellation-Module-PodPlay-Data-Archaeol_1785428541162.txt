# Phase 0 — Auto-Cancellation Module: PodPlay & Data Archaeology

**Mode:** READ-ONLY. Audit and report. No implementation.
**Estimated scope:** 9 items, all independent.
**Deliverable:** a written report following the format in §Report Format. No code changes, no new files except the scratch artifacts named in the items.

---

## Context

We are scoping a standalone background service that will, some fixed interval before a program's start time, check its signup count and — if under a configured threshold — cancel the program and notify registrants by email and SMS.

Before any of that gets built we need to know what the PodPlay API actually permits, and what our own historical data says about when people book. Everything here is reconnaissance. Answers determine the architecture; wrong assumptions here are expensive later.

Known API facts (do not re-derive, but do verify if a step contradicts them):

- Base URL: `https://pbclub.podplay.app/apis/v2`
- Auth: `x-api-key` header. **Not** `Authorization: Bearer`.
- OpenAPI spec: `GET /apis/v2/docs-json`
- Known-good endpoints: `GET /events`, `POST /events/clones`, `PATCH /events/{eventId}`, `GET /events/{eventId}/signups`, `GET /users/{userId}/phone-number`, `GET /users/{userId}/ratings`
- There is no create-event-from-scratch endpoint; publishing is clone-then-patch.
- The `userId` filter on `GET /events` is a no-op — ignore it.
- `signups` (currently registered) and `attendees` (historical) are different endpoints. Do not conflate them.

## Item 3 — Cancellation mechanism identification

**Read-only. Identify. Do not invoke.**

From Item 1's spec and Item 2's object shape, determine which of these describes reality:

- **(a) Dedicated endpoint** — e.g. `DELETE /events/{eventId}` or `POST /events/{eventId}/cancel`. Report the exact path, method, required path/query params, request body schema, and documented response.
- **(b) Status field via PATCH** — cancellation is expressed by patching a lifecycle field on the event. Report the exact field name, the value that means cancelled, and the full minimal request body that would accomplish it.
- **(c) Neither exists** — no documented cancellation path.

If (c), that is the single most important finding in this audit and it changes the product: the module becomes an alerting tool that tells a human to go cancel in the PodPlay UI, not an automated canceller. Say so plainly.

Also report whether the spec documents anything about **reversibility** — can a cancelled event be un-cancelled, or is it terminal? If terminal, every downstream design decision needs to be more conservative.

Again: identify the call, write down its shape, do not make it.

## Item 5 — Does PodPlay already notify on cancellation?

Search the spec for any indication that cancelling an event triggers PodPlay-side participant notification — an email, a push, an in-app message.

Look for: a `notify` / `sendNotification` / `silent` flag on the cancellation or update request; any mention of participant notification in endpoint descriptions; any notification-related endpoints at all.

Why this matters: if PodPlay already emails registrants on cancel, our module should **supplement** (SMS, custom copy, alternative-session suggestions) rather than own the notification, and we must avoid double-emailing. If PodPlay is silent on cancel, we own the entire notification path and it becomes the critical piece of the build.

If the spec doesn't say, mark it undocumented and flag it as needing a live test in the deferred step.

## Item 7 — Signups endpoint shape

This item likely determines the notification architecture. Read it carefully.

Call `GET /events/{eventId}/signups` for a real upcoming event with a non-trivial number of registrants.

Dump one complete signup object as unmodified JSON (redact PII values, keep the structure and field names).

Then report:

- **Does the signup object include the registrant's email and/or phone inline?** This is the key question. If yes, notification is one API call per event. If no, it's N+1 per-registrant lookups executed inside a tight pre-start window — a materially worse design under time pressure and rate limits.
- Is there a waitlist concept? Are waitlisted people in this response, and are they distinguishable from confirmed registrants?
- Can a signup be in a cancelled/withdrawn state and still appear in the response? If so, a naive `length` count overstates real enrollment — which would make our threshold check wrong in the dangerous direction.
- What is the correct way to derive a **confirmed signup count** from this payload? State it precisely; this is the number the entire module is built on.
- Is the response paginated? If so, what are the parameters and the default page size?

## Item 8 — Rate limit characterization

The proposed design ticks every 5 minutes, listing events and then fetching signups only for the small number entering the decision window. Validate that this is safe.

Sequentially call `GET /events/{eventId}/signups` for 20 different upcoming events. Record per-call latency and any non-200 responses.

Report: p50 latency, max latency, any 429s or throttling, and any rate-limit headers present on responses (`X-RateLimit-*`, `Retry-After`, or equivalent). Also time a single `GET /events` call over a 14-day forward window.

Do not exceed 20 signups calls. If you hit a 429 before 20, stop immediately, record where it happened, and report — that's a finding, not a failure.

## Item 9 — Late-booking curve from historical data (Supabase, read-only)

The threshold and the decision offset should come from PB Club's actual booking behavior, not a guess. This is reconstructable from data we already have.

`attendances.booked_at` is a real PodPlay signup timestamp (`signup.summary.invitation.createdDate`), and `attendances.attended_at` has been `timestamptz` since the 2026-05-07 migration — so for any past event we can count how many people had signed up as of N hours before start.

For events in the last 120 days, produce:

1. **Coverage first.** How many attendance rows in the window have non-NULL `booked_at` and non-NULL `event_id`? What percentage? If coverage is poor, everything below is unreliable and the item should be marked PARTIAL with the coverage number as the finding.
2. **Per-event point-in-time counts.** Treat each `event_id`'s `attended_at` as the event start. For each event, compute the signup count as of T-1h, T-2h, T-4h, T-24h, and the final count.
3. **The late-booking curve.** Across all events: what fraction of final signups had booked by each cutoff? Report as a distribution (p10 / p50 / p90), not just a mean.
4. **The counterfactual.** For candidate rules of the form "cancel if count < N at T-2h," for N in 2 through 8: how many of the last 120 days' events would have been cancelled, and of those, **how many ended up with a final count at or above N**? That last figure is the false-positive rate — sessions we would have killed that were going to be fine. This is the number that sets the threshold.
5. **Segment it.** Break the T-2h fraction down by program type and by weekday-evening vs other time bands. If prime-time weeknight open play fills late and morning clinics don't, the rules engine needs per-archetype offsets and we should know that now.

Two caveats to state explicitly in the report:

- `attendances` rows exist for people who signed up; if PodPlay signup cancellations delete or never create rows, withdrawals are invisible and counts may be optimistic.
- If `booked_at` was backfilled rather than captured live for older rows, early data may be unreliable. Note the earliest date at which `booked_at` looks trustworthy.

Save the full per-event result set to `/tmp/phase0/late-booking-curve.csv` and summarize in the report.

**Live cancellation test.** Whether cancellation actually works, what it does to payments, and whether PodPlay emails registrants can only be settled by cancelling something real. That requires a throwaway event created via clone, cancelled deliberately, with the effects observed — and it needs its own gated prompt and a human watching. Do not attempt it here under any framing.
