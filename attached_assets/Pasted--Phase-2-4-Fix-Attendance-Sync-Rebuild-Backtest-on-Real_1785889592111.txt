# Phase 2.4 — Fix Attendance Sync, Rebuild Backtest on Real Ground Truth

**Mode:** Build. No execution path — nothing here can cancel an event, message anyone, or write to PodPlay.
**Scope:** 3 items, sequential. Item 1 must complete and re-sync before Item 2 runs.

---

## Context

Phase 2.3 delivered a working reconstruction, but the resulting numbers are not yet trustworthy for two reasons — one a data defect, one a definitional one.

**1. The attendance sync drops series-clinic participants.** `syncEventAttendance.js:152` uses `VALID_SIGNUP_STATUSES = {CONFIRMED, CHECKED_IN}`. Phase 2.2 established that `INVALID` marks **completed multi-session series-pass enrollments** — real participants. This is the same bug fixed in `eventFillSync.ts` and `programmingEvaluator.ts`, one layer deeper: it means `attendances` rows were never created for series-clinic participants at all. Spot-checks showed 2 local rows against 4 PodPlay signups.

The backtest reconstructs enrollment-at-offset from `attendances.booked_at`, so this undercount feeds directly into every number it produces.

**2. The "true positive" definition is a proxy, not an outcome.** The current backtest scores a fire as correct when `fill_rate < 0.5`. That measures the rule against a second arbitrary rule, not against reality. A session that reached 5 of 12 and ran fine is counted as correctly cancelled.

Real ground truth is available and directly computable: **a false positive is a session the rule would have cancelled that reached the threshold by start time.** That's the Phase 0.6 definition and it needs no proxy.

Both defects push the same direction — inflating apparent false positives — so the Phase 2.3 grids (56.6% Open Play, 90.2% Clinics at N=4/T-3h) are upper bounds of unknown tightness. The Clinic-vs-Open-Play *separation* is trustworthy (both segments carry the same bias, and 41pp is far outside both bands). The *absolute levels* are not, and must not inform a threshold change or go in front of stakeholders until this phase closes.

## Item 2 — Rebuild the backtest on real cancellation outcomes

**2a. Replace the outcome definition.** Remove the `fill_rate < 0.5` proxy entirely. Ground truth per event:

- **Would-fire:** reconstructed enrollment at the checkpoint offset < N
- **Actual outcome:** the event's final active signup count (from `event_fill`, corrected), and its `isCanceled` status
- **False positive:** would-fire AND final count ≥ N — the rule would have killed a session that reached threshold
- **True positive:** would-fire AND final count < N

Events already cancelled in reality need explicit handling: their final count is truncated by the cancellation, so they can't be scored as either. **Exclude them and report the count separately.** Do not score them as true positives — that assumes the cancellation was correct, which is the thing under test.

**2b. Keep the existing coverage gates.** Per-event `booked_at` coverage ≥ 90%; report exclusions. Per-archetype local-vs-PodPlay ratio check with a stated floor; report any archetype excluded and why. Both should behave better after Item 1.

**2c. Report residual undercount.** Even after the fix, `attendances` may lag PodPlay for very recent bookings or unmatched signups — the last sync logged 97 unmatched. Quantify what remains: on a sample of past events, the ratio of local rows to PodPlay active count, and specifically how many bookings land inside the final 3 hours and would be invisible at a T-3h checkpoint.

**This is the number that bounds the whole result.** State it prominently rather than in a footnote.

**2d. Validate.** Re-run Social Open Play at N=4/T-3h.

Expect the FP rate to come in **below** Phase 2.3's 56.6%, since both fixes removed sources of inflation. If it comes back higher, something is wrong — report rather than proceeding.

Also confirm it is not near zero. Near-zero was the signature of the original broken approximation.

**2e. Report `n` and uncertainty** as before: median usable rows per event alongside every percentage, presented with the resulting band rather than to three decimals.
