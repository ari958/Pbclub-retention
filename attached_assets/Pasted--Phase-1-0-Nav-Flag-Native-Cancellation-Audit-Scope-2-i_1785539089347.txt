# Phase 1.0 — Nav Flag & Native Cancellation Audit

**Scope:** 2 items. Item 1 is a small reversible frontend change. Item 2 is read-only analysis that reports back.
**Deliverable:** Item 1 implemented; Item 2 reported per §Report Format. No UI built for Item 2 yet — we decide what to build after seeing the data.

---

## Context

We're refocusing the dashboard onto a new feature area — a programming agent that decides what programs to run, when to change them, and when to cancel them. Pulse's retention surfaces are being hidden, not removed.

The first real screen will be an audit of what PodPlay's **native** auto-cancel has already done. Background: 95 of 270 upcoming PB Club events have `lowTurnoutAutoCancelAttendeeCount: 4` and `lowTurnoutAutoCancelHoursBefore: 3` (some at 8h) configured. Against the club's own booking history, N=4 at T-3h has a modeled false-positive rate of ~44% — roughly half the sessions it cancels would have reached 4+ players by start time.

Item 2 replaces that model with the actual list.

---

**4. Never echo secrets.**

## Item 2 — What has the native canceller actually cancelled?

Read-only. This is the analysis behind the first real screen.

### 2a. Find the cancelled events

`GET /events` with `includeCanceled=true` over the last 120 days. Use the documented query params (`startTime`, `endTime`, `page`, `ipp`) rather than fetching everything and filtering client-side.

Identify cancelled events. Check the event object for `isCanceled`, and also `GET /events/{eventId}/cancellation` on candidates to retrieve the cancellation record where one exists.

Report: total events in window, how many cancelled, and what fields distinguish a cancelled event.

### 2b. Attribute each cancellation

For each cancelled event, record:

| Field | Source |
|---|---|
| event id, name, start time, program type | event object |
| `lowTurnoutAutoCancelAttendeeCount` / `HoursBefore` | event object — was native config set? |
| cancellation `reason` | `GET /events/{eventId}/cancellation` |
| `cancellingUser` | same — human admin vs. system vs. `API Key Access` |
| cancellation timestamp | same |
| hours before start it was cancelled | computed |

The key split: **which cancellations came from the native low-turnout rule, and which were human decisions** (weather, coach illness, facility). If `reason` is `LOW_TURNOUT` and native config was set and the cancellation landed at roughly the configured offset, attribute it to the native rule. State your attribution logic explicitly and report how many cancellations are ambiguous.

### 2c. The counterfactual

This is the number that matters. For each cancellation attributed to the native rule:

- Signup count at cancellation time (from `attendances.booked_at` where available, or the cancellation record if it carries one)
- **Would it have filled?** There is no post-cancellation booking data — once cancelled, nobody else could sign up. So estimate from the archetype's historical curve: given `k` signups at T-3h for this program type and slot, what fraction of comparable *non-cancelled* events reached 4+?

Be explicit that this is an estimate, not an observation. Report the comparison set size for each estimate. Where the comparison set is under ~10 events, say so rather than reporting a percentage.

### 2d. Summarize

- How many sessions has the native rule cancelled in 120 days?
- Estimated false positives, with the uncertainty band
- Total registrants affected — people who had booked and got cancelled on. Cross-reference to `players` and report how many are currently `lapsing` or `dormant`. **A player who was cancelled on and then stopped coming is the churn story this whole product is about.**
- Break down by program type. Clinics vs Open Play is expected to differ sharply.

Save the per-event table to `/tmp/phase1/native-cancellations.csv`.
